## 二、官方协议摘要（可执行版）

### 2.1 两种结构的字段（顺序固定）

**无参考图 / 关键帧**（T2VA / I2VA / FL2VA / L2VA）：
```
integrated_multimodal_description:
overall_soundscape:
non_diegetic_music:
```

**全参考**（Ref2VA，我们用二采就是这条）：
```
subject_definitions:
summary:
retention_analysis:
detailed_description:
overall_soundscape:
non_diegetic_music:
```

### 2.2 图片对齐指令（只有 I2VA/FL2VA/L2VA 才有）

必须放在**第一行**，后接**一个空行**，再进正文。官方给了固定句式：

- I2VA：`For the target video, at 0.00 seconds into the target video, <Picture 1> (from [Shot 1]) is fully referenced.`
- FL2VA：`How the reference pictures align with the target video — Picture 1 (from Shot 1) aligns with the 0.00-second mark of the target video; Picture 2 (from Shot N) aligns with the S.SS-second mark of the target video.`
- L2VA：`How the reference pictures align with the target video — <Picture 1> (from [Shot N]) aligns with the S.SS-second mark of the target video.`
- T2VA：**没有**这一行。

### 2.3 镜头与切点

- `[Shot 1]` **不写时间码**；后续写 `[Shot N] At 00:03.500, ...`，**严格递增**且落在时长内
- 普通切换用 `the camera cuts to` / `the shot transitions to` 等；只有用户明确要求才用 cross-dissolve / fade / wipe
- 切点必须带来新信息（主体/空间/状态/视角/时间）。**只是景别或轻微角度变化，优先用运镜而不是切镜**

### 2.4 运镜 = 类型 + 幅度 + 速度

固定词表 13 个：`Zoom In/Out`、`Push In/Pull Out`、`Pan Left/Right`、`Truck Left/Right`、`Tilt Up/Down`、`Pedestal Up/Down`、`Arc Shot`、`Tracking Shot`、`Static Shot`、`Shake Slightly/Strongly`、`POV`、`Roll Clockwise/Counterclockwise`。
幅度：`with small amplitude` / `with large amplitude`；速度：`at slow speed` / `at fast speed`。中等幅度与常速**省略不写**。
必须写成自然动作句：`The camera pushes in with small amplitude at slow speed toward the folded letter in her hands.`

### 2.5 对白与声源

- 会有声音的人用**稳定 ID** `(S1)` `(S2)`；多人齐声 `(S1,S2)`；**不发声的人不分配 ID**；同一人跨镜同一 ID
- ID、说话人身份描述、动作、语气**全部写在 `<d>` 外面**；`<d>` 里**只有**语言标签 + 逐字原文：`<d>[English] I get off at the next station.</d>`
- 画外音固定短语 `says in an off-screen voiceover`，**紧接**说明画内人物嘴闭合
- 跨切点：`<scenetrans>` + 明确音频连续；被片尾截断：`<cutoff>`
- 画面可见文字用**英文双引号**并逐字保留：`A red neon sign reading "营业中" glows above the doorway.`

### 2.6 两条声音字段的职责（官方写得很死）

| 字段 | 写什么 | 不许写什么 | N/A 条件 |
|---|---|---|---|
| `overall_soundscape` | 1–4 句，**整段**环境声、物理动作声、非语言人声的**概括** | 对白、歌唱、有源音乐；**逐镜同步的具体音效**（那些留在 `detailed_description`） | 只有用户明确要求**全片完全静音** |
| `non_diegetic_music` | 1–3 句，乐器、速度、节奏、强弱变化 | **抽象情绪词**、解释配乐的情感作用；角色能听见的音乐（属 diegetic，写进正文） | 没有非叙事配乐时写 `N/A` |

### 2.7 参考标签与 retention 标记（全参考模式）

四类标签：`<Subject N>`（可复用的可见内容）、`<Picture N>`（作为具体帧/构图锚的参考图）、`<Video N>`（整条视频的结构/编辑源）、`<Audio N>`（音频信号）。
**标签一旦分配，含义跨全部六段保持一致。**

`<Picture N>` 什么时候才单列一条：**只有当它本身充当某镜的首帧/关键帧/末帧/构图锚时**。
> 如果一张图只是用来定义角色 / 场景 / 服装 / 风格，**不要单列 `<Picture N>` 条目**，把图源写进对应 `<Subject N>` 的定义里。

retention 标记是**固定英文值**：

| 可见内容 | 含意 | 音频 | 含意 |
|---|---|---|---|
| `fully_preserved` | 定义的角色完全保留 | `fully_copy` | 整条音频 1:1 作为最终音轨 |
| `partially_preserved` | 仍在用，但部分特征变了 | `partially_copy` | 只复制部分时间线/图层，或复制后又增删改 |
| `attribute_transfer` | 特征转移到另一个可识别主体 | `reference` | 不复制信号，只参考音色/节奏/风格/内容 |
| `weak_reference` | 只保留风格/类别/氛围的宽泛相似 | `weak_reference` | 只保留类别或氛围的宽泛相似 |

条目格式：`<Subject 1> (appears in [Shot 1], [Shot 3]): fully_preserved - ...`（**逗号列举镜号**，不是 `through`）。

### 2.8 篇幅

- 全参考模式的 `detailed_description`，生成任务**通常 350–500 英文词**；对白密集时优先装下完整发话时间线，不机械凑字数
- 风格总述放在 `[Shot 1]` **之前**，一到两句英文

## 五、结论：我们错在哪

**根因一句话**：我们的 `prompts/h3-r2v-提示词格式.md` 是**从两份样本反推**的，不是从规范来的。样本能反映"某个人怎么写"，不能反映"协议要求怎么写"。于是：

1. **把离群样本当成了规则** —— 15s/5 镜 11,270 字的主体，官方给生成任务的指引是 350–500 **英文词**，差了一个数量级；我们却把它写成「进阶版密度」，还解释了理由（「给二采准备」），这个理由是我们编的。
2. **把「逐镜音效清单」写进了 `overall_soundscape`** —— 官方明说那一段是**整段声学概括**，逐镜同步音效留在正文里。这条错会被模型照做。
3. **整层缺失** —— 对白 `(S1)`/`<d>`/`<scenetrans>`/`<cutoff>`、参考音频 `<Audio N>`、图片对齐指令行。这些不是"可选的写法风格"，是协议的一部分。
4. **单列 `<Picture N>`** —— 官方明确说仅用于定义角色时**不要单列**。

这解释了我上次写坏提示词的深层原因：**我手里那份"格式规范"本身就是错的**，再让弱模型照着它写，错上加错。

## 六、工具应该怎么做

### 6.1 分层：谁负责什么

```
AI（写手：写正文、做取舍）
   ↓ 交付 JSON：正文 + 元数据（分镜列表、参考图槽位、声源映射）
【本地契约层】← 只校验形状与协议结构；不解读内容、不改正文、不补剧情
   ├ h3protocol.mjs  结构校验（六段/三段、切点、对白标签、禁用字段）
   └ h3refs.mjs      <Picture n> 编号从 API 图推导（不确定就返回 undefined）
   ↓ 不通过：带字段路径的中文错误（只报形状）→ 回给 AI 自己改
   ↓ 通过
comfy_video 提交（一采 → SplitSigmas 8+4 二采）
```

原则（照官方 + 对方共同指向的）：
1. **程序不写正文**。只判断"结构对不对"。
2. **不确定就拒绝，不猜**。编号推不出来就报错，而不是给个大概率对的数。
3. **报错只报形状**，不带正文，避免把长提示词塞回上下文。
4. **可选元数据坏了不阻断交付**。

### 6.2 四步，每步有成功标志

**第 0 步 · 修两个既有缺陷（半天，最高优先）**
- `mcp/lib/comfy.mjs` 的 `waitFor`：任务从队列消失不再立刻抛错，改为「≥30 分钟 + 连续 6 次有效观测 + 跨度 ≥2 分钟」才判定消失
- `/queue` 只留 id/在场信息 + 1s TTL 缓存，不再整包拉
- **成功标志**：故意让一个任务中途从队列消失，工具不报「id 写错了」，而是继续等或明确说「无法确认」

**第 1 步 · `mcp/lib/h3protocol.mjs`（纯函数，无 GPU）**
校验项：六段/三段字段名与顺序；`[Shot 1]` 无时间码；后续 `At MM:SS.mmm` 严格递增且在时长内；`<d>` 配对闭合；`(S n)` 只在有对白时出现且首次出现顺序递增；`<Subject n>`/`<Picture n>` 引用必须先在 `subject_definitions` 定义；`overall_soundscape` 里出现逐镜列举就告警；禁止 `negative_prompt`/`negative`/`[Shot 0]` 之类非法标记。
- **成功标志**：官方 4 个 case 全过（正样本）；6 条故意写坏的（切点倒退、`<d>` 未闭合、引用未定义标签、出现 negative、首镜带时间码、齐声写成两个独立 ID）全被抓到

**第 2 步 · `mcp/lib/h3refs.mjs`**
从 API 图推 `<Picture n>`：`MiniMaxH3ImageToVideo` 按 `first_frame, last_frame`；`MiniMaxH3ReferenceToVideo` 按 `ref_images.ref_image_N` 插入顺序；只跟随单图操作（ImageScale/Crop/Flip/Reroute）；遇到 switch/batch 标 unresolved；同一图源被两槽使用 → 返回 undefined。
- **成功标志**：在我们那份二采图上推出一致的编号；对「一图两用」明确拒绝

**第 3 步 · 接进提交链**
`comfy_video` 提交前跑上面两个；不通过就不提交，返回带字段路径的问题清单。
- **成功标志**：故意写错一次，工具列出问题且**没有**发起 5 分钟的执行

**第 4 步 · 改写 `prompts/h3-r2v-提示词格式.md`**
改成「官方规范为准 + 我们那份样本作为实例」，把第 3 节列的 14 条差异逐条标注；删掉我们自己编的「进阶版密度」解释。
- **成功标志**：文档里每条规则都能指到官方 `base-en.txt` / `ref-en.txt` 的行，或明确标注「这是我们自己的选择」
