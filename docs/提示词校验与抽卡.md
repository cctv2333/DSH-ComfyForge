# 提示词校验器 + 低清抽卡（以及为什么不上小模型做主力）

- 日期：2026-11-04
- 起因：① 提示词写对与否，现在只能靠人眼；② 出片好坏"认命"，没有筛选环节。
- 结论先行：**校验器规则层做主力（100 条判据、0 依赖、毫秒级），小模型只当可选的语义层**；抽卡走"低清草片 → 客观指标排序 → 只精修前 K 条"。

---

## 一、为什么不是"全交给小模型"

你问的方向是对的——小模型确实能判一些规则写不出来的东西。但把它放到主力位置会有三个具体代价，在这台机器上尤其明显：

| 代价 | 具体表现 |
|---|---|
| 抢资源 | 本机 RAM 空闲约 2GB、显存 8GB 且出片时被 ComfyUI 占满。跑一个 1.5B 模型要么挤爆内存，要么和出片排队 |
| 假阳性 | 小模型对"结构是否齐全"这类**有唯一答案**的问题反而容易说错（把合规的判成不合规），人还得回去复核，等于没省事 |
| 不可复现 | 同一段提示词两次跑可能给不同结论；规则层永远给同一个答案，能进 CI、能写进档案 |

所以分工是：

- **规则层**（默认，永远开）：结构、段落、指代闭合、分镜编号、时间码单调、每镜手分工/声画同步、帧数 5+17k、字数密度、绝对化/否定措辞计数。**有唯一答案的全在这里。**
- **语义层**（可选，`--llm`）：左右手是否自相矛盾、动作物理上做不到、风格声明与内容冲突、跨镜主体漂移。**规则写不出来的才问模型**，而且只产出 warn，不阻断。

## 二、用法

```bash
# 规则层
node tools/prompt-lint.mjs prompts/examples/黑鹤派-流萤做饭-15s-5镜.txt --seconds=15 --images=1

# 加语义层（需要本地端点）
node tools/prompt-lint.mjs 我的提示词.txt --seconds=15 --images=1 --llm

# 给别的工具吃
node tools/prompt-lint.mjs 我的提示词.txt --seconds=15 --json
```

MCP 侧同步加了 `comfy_lint_prompt`（file/text/seconds/ref_images/llm），**重启 DSH 后生效**。

### 实测判分

| 提示词 | 分 | 判定 | 说明 |
|---|---|---|---|
| 黑鹤派 15s 五镜（一手样本） | **100** | 可以发 | 六段齐、5 镜、时间码递增、每镜有手分工 |
| 官方 r2v 模板 5s（极简样本） | 78 | 可以发 | 缺 summary/retention/detailed 三段的"进阶结构"，但这是它本来的写法，不算错 |
| 故意写的坏样本 | 6 | 有错误 | 抓到：时间码 4s 在 8s 之后、分镜编号 1→3→2、`<Picture 2>` 但只给 1 张图、每镜没手分工、20 字/秒太薄、没写 BPM |

坏样本那次一共报了 **1 错误 + 11 警告 + 8 提示**，每条都带一句"怎么改"。

### 语义层怎么接（不下载、不捆绑）

工具本身**不带任何模型运行时**，接任何 OpenAI 兼容端点：

1. **Ollama**（最省事）：`ollama pull qwen2.5:1.5b-instruct`（约 1.0GB），端点自动是 `127.0.0.1:11434`，不用配。
2. **llama.cpp server**：下一个 Qwen2.5-1.5B-Instruct-Q4_K_M.gguf（约 1.0GB），`llama-server -m 文件 --port 8080`。
3. **远程**：设 `PROMPT_LINT_LLM_URL` / `PROMPT_LINT_LLM_MODEL` / `PROMPT_LINT_LLM_KEY`。

没有端点时它**不会静默跳过**，而是把上面这段安装说明原样打印出来（工具要能告诉人"缺什么、多大、怎么补"）。

> 关于"自动下载"：我不做自动下载，只做**探测 + 打印确切命令**。理由是自动下模型要么在别人机器上悄悄占 1GB 磁盘，要么在断网时卡住；而"给一条能复制的命令"成本更低、更可控。这是有意的取舍，不是没做。

## 三、低清抽卡

```bash
node tools/sweep.mjs .cache/cfg-sweep.json
```

```jsonc
{
  "image": "图片-流萤Q版三视图正脸图.jpeg",
  "prompt": "...",           // 会先过一遍校验器，有 error 直接拒跑
  "seconds": 1.6,
  "seeds": [111, 222],
  "width": 608, "height": 352,
  "steps": 8,                // 草片步数，便宜
  "refineTop": 1             // 前 1 名再走二采精修
}
```

**为什么是低清 + 跑满**：草片必须是一采**跑满 sigma** 的完整画面（608×352、8 步，39 帧约 60 秒），不是半截 latent——半截 latent 解出来是马赛克，看不了。成本约高清单遍的 1/4。

**排序不用眼睛**：每条草片算 `videoMetrics`（帧间差分/黑帧/强切点/音量），按分排序；同时拼一张对照图，人只用看**已排序的前几条**。

**输出**：`runs/sweep-<时间>.md`（排名表 + 每条的指标 + 文件路径）、`.cache/sheets/sweep-*.png`（对照图）、精修结果。

## 四、关于 comfyui-mcp：不装，但抄三样

`comfyui-mcp`（[artokun/comfyui-mcp](https://github.com/artokun/comfyui-mcp)，npm 上的 `comfyui-mcp-multiagent`）是真实项目：89–96 个 MCP 工具、22 个 skill、4 个 agent（explorer / **debugger** / **optimizer**）、hooks（执行前显存看门狗）、WebSocket 实时进度监控。

**不装的理由**：它是**一整套 MCP server**，装进来等于把我们这 32 个工具重铺一遍，还带 npm 依赖链和 Claude Code 插件形态——和你"资源少、别搞插件收集器"的约束直接冲突。它的价值在**做法**，不在代码。

**值得抄的三样（按价值排序）**

| 它做的 | 我们的现状 | 我们的做法 |
|---|---|---|
| `/comfy:debug`：读 history + 日志，**定位到具体失败节点**并给修复 | `comfy_log` 只给错误行 + 一段 traceback，没有"是哪个节点、该改什么" | 下一步做：traceback → 节点 id/class 映射，结合 `comfy_check_workflow` 的 A/B/C/D 分类给出改法 |
| `monitor-progress.mjs`：WebSocket 实时进度（"step 5/14 36%"） | 只有整单的 pending/elapsed | 下一步做：把 progress 打进 `videoStatus`，长任务能报"第 120/362 帧" |
| VRAM watchdog hook：执行前查显存，低了先警告 | `comfy_health` 只在开头查 | 便宜，可以在 `submit` 前顺手查一次 |

**不值得抄**：模型下载/注册表/Civitai 对接/skill 生成——我们用不上，且引入网络依赖。
